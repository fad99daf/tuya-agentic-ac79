## 1.5 「逐条明细」页签逐条挖掘（798 行 × 18 列，2026-09-15 补充）

> 报表匹配口径：云端 VAD/ASR 匹配窗 7000ms、云端打断 5000ms，顺序保持的一对一最优对齐。

**① 词错类型构成——"漏词"主导，缺字型错误实锤 P0**
全量 S替换=162 / **D漏词=305** / I多词=17（总错误 484）→ **漏词占 63%**；识别相似度中位仅 0.33，
完全命中（=1.0）只有 4%。错误形态是"整段词没上去"而非"听错了"——指向音频缺失/迟到，不是模型
识别混淆；多词(I)≈0 也说明不是噪声词混入。

**② 打断延迟存在 ~3s 的场景无关地板**
打断命中样本 n=169：**med=3261ms，p90=3801ms，<1.5s 的仅 10%**。关键对照：AEC-quiet 的 VAD 延迟
中位只有 469–557ms，打断延迟却仍是 ~2.9–3.2s——即使在最好条件下，打断路径也要 ~3s（上行滞后 +
云端 VAD 判定 + 事件下发）。这是独立于能量门（P1）的链路性开销，S1/S2 落地后应作为专项复测指标。

**③ 会话内随时间退化（长连接老化证据，tai 重构对症点）**
同为 AEC+10dB 的三段重复场景，随会话进行持续下滑：

| 场景 | 时段 | VAD 检出 | ASR 识别 | 打断命中 | 误打断 |
|---|---|---|---|---|---|
| 3AEC10db | 16:41 | 40.0% | 30.0% | 8.3% | 75% |
| 6AEC10db | 17:01 | 23.3% | 20.0% | 3.3% | 87% |
| 9AEC10db | 17:21 | **3.3%** | 5.0% | **0%** | 100% |

安静组同样后段走低（35.0% → 36.7% → 25.0%）；xin0db 场景内前/中/后三等分命中 15→9→9。
旧代码无连接保活（当日日志 Http reconnect ×7）与此吻合——**已合入的 30min ConnectionRefresh
（TAI_CONN_REFRESH_INTERVAL_MS）正对症，这是重测最能直接验证 tai 重构收益的一项**。

**④ VAD 命中了但 ASR 没跟上：84 次**
云端检出语音起点共 217 次，其中 84 次在 7s 窗内没有产生 ASR 请求——起点检到了、音频本体跟不上/
提前结束，同样是 P0 的云端侧表现。

**⑤ 与说话内容、分型无关（排除词条/唤醒词因素）**
- 长句"讲一个长故事"（n=366）VAD 28% vs 各短句 15–33%，无显著差异；
- AEC 场景 wake(唤醒词)/test(命令词) 分型命中率基本持平（如 2AEC：13/30 vs 8/30）；
→ 问题呈链路性，不是特定词条或唤醒词问题。

**⑥ 噪声越大检出反而越高（0db→20db：22.9%→31.3%）**
云端 VAD 不是被噪声"淹没"，而是受设备侧送音频的实时性/完整性限制——最吵的 20db 场景反而最好，
因为大声说话在丢帧/降噪压缩后残留的能量更多。与 P0/P2 解释一致。

**⑦ 报表口径提醒（给测试团队）**
明细页 141 条 ASR 记录的识别文本 100% 非空，但设备日志 eof 空 text 占 34.7%（389/1121）——空识别
请求未进入报表匹配口径。建议报表补"设备侧 ASR 请求总数 / 空识别数 / 报表匹配数"三口径对照，
否则空识别问题在报表里不可见。另：1 个 VAD、4 个打断事件落在所有场景时间窗之外（信息性）。

## 2. 根因分析（按影响排序）

### P0 上行管线吞吐不足（影响：VAD 检出、VAD 延迟、ASR 空/WER —— 即报表大头）
- **结构**（tuya_agentic_demo.c:1876 起上行循环）：单线程「读 PCM(≤40ms 等待) → opus 编码 → 阻塞式
  `tai_send_audio_chunk`」。新版 SDK 发送路径每帧拆 3 次 `tls_write`（帧头/负载/签名，tai_client.c:190-198），
  阻塞超时 10s（tai_client.c:74）。
- **缓冲**：mic cbuf 仅 500ms/16000B（audio_input.c:797-798），溢出丢最旧一帧（drop-oldest）。
  循环只要平均帧耗时 >40ms 就持续丢音。
- **观察者效应（嫌疑最大）**：`TUYA_UPLINK_LATENCY_DEBUG`（demo.c:65）硬开，说话期每帧打印；
  SDK `[pkt]` 全量 JSON 收发包日志开启（demo.c:2760 `TUYA_SDK_LOG_LEVEL=LOG_INFO`）。两者共用一条
  UART，打印阻塞会直接拖慢发送循环——与"空闲 40ms 精确、说话期 60ms"的特征吻合。
- **云端后果**：音频迟到+有洞 → 云端 VAD 起点晚 1–3.9s 甚至检不到；ASR 缺字/空识别。

### P1 打断能量门限与真实信号失配（影响：打断命中率 21%、9A/4A70 打断 0%）
- 门限固定：`BARGE_MIN_ENERGY=100000`（demo.c:94）、`BARGE_CONFIRM_ENERGY=600000`（demo.c:99，9/4 按
  **安静室**校准：真人 ≥115.9万、AEC 残留 ≤38.4万）。
- 但 9/2 测试（dB65 噪声 + P2 的 DNS 压缩）话音 onset 帧能量中位仅 **~10 万**——比确认门低 6 倍。
- 9/2 日志里存在 sum=16.3万/45.4万/15.2万 的真实打断确认（15:10:18）；**这类打断在当前 600k 门下会被拒绝**。
  即：固定门限在"安静室防误触"与"噪声场景保命中"之间结构性不可兼得。

### P2 降噪过抑制（放大 P1、拉高 WER）
- user_cfg.c:301-302 强制 `DNS_over_drive=3.0f`、`DNS_gain_floor=0.1f`，且强制开 DNS（BIT(5)）。
- 代码注释自证后果："实测说话帧 act 0~2%，与底噪同量级"。说话被压到接近底噪 → 能量门失灵、ASR 缺字。

### P3 4A70 云端轨迹缺失（非设备问题）
- 4A70 时段设备日志有正常 ASR 文本与 confirm 能量，链路健康；报表"零云端 VAD 事件"是云端轨迹导出/匹配
  侧的问题，需云端/测试平台侧核查。

### 已合入修复覆盖的是次要因素（不是上述根因）
- tai 客户端重构（确认式连接/ping 探针/fail-fast/30min 连接保活）：改善会话中断与长连接回收 →
  报表中"疑似链路异常"类损失会减少。
- 下行 audio-params 按流重协商、轮次 id 闩锁：修连续轮 TTS 分帧错位与旧轮 END 误收尾。
- MYWO-13/14：云端连接等网络就绪、配网提示音门控；MQTT 心跳提速（DP 下行 5s→10ms，音量类指令实时性）。
- 9/4–9/6 barge-in 修复（3/3 确认、onset prefill、吞咽窗）：**安静室**打断体验/误触改善。

## 3. 解决方案（按优先级）

### S1（立即，零风险）：关诊断打印，重测一轮 —— 先裁定 P0 归属
1. 注释 demo.c:65 `#define TUYA_UPLINK_LATENCY_DEBUG`；
2. demo.c:2760 `TUYA_SDK_LOG_LEVEL` 改 `LOG_WARN`（关 [pkt] 收发包 JSON）；
3. 保留 SDK 新埋点（tai_client.c:76：`tls_write≥50ms` 自动告警）判网络/TLS 开销。
   - 若改完后每帧恢复 40ms、丢帧归零 → 根因确认是 UART 打印；若仍 60ms → 看
     `[ctx_io_send] tls_write=` 告警定位 TLS/网络，再进 S2。

### S2（短期，开发量小）：上行"读与发"解耦 + 缓冲扩容
- 独立发送线程 + 环形队列：上行循环只做 读→编码→入队；发送线程批量取帧、合并成一次
  `tls_write`（同时消除新版每帧 3 次 write 的开销）。发送失败置 `g_link_broken` 语义不变。
- mic cbuf 16000B → 64000B（500ms→2s，RAM 够：日志显示堆剩 4.8MB）；
- 溢出丢帧加计数器并周期打印，作为重测的核心指标。

### S3（P1）：能量门改自适应
- 数据源现成：idle drain 每 16 帧(640ms) 已算 `avg_sum`（demo.c:1977）——把它存为滑动底噪基线 B。
- 建议：`MIN = max(100k, 20×B)`、`CONFIRM = max(300k, 100×B)`（按安静底噪 B≈300、真人 onset≈10万
  反推的系数，需实测微调）；保留 3/3 确认与持续时间判据；AEC 场景可叠加"底噪突变率"判据替代单一幅值。

### S4（P2）：DNS 参数试验矩阵
- `DNS_over_drive` {2.0 / 2.5 / 3.0} × `DNS_gain_floor` {0.1 / 0.2}，user_cfg.c:301-302；
- 验收指标：WER、VAD 命中、AEC 误打断率三者联合看（2.0 降噪弱可能抬误打断）。

### S5：重测方法论
- 同场景 AB 两版固件：宏开（对照，量化观察者效应）vs 宏关；
- 每轮记录：发送帧数/丢弃帧数/每帧间隔 p50/p95/云端 ASR 输入时长；
- 专项一（打断延迟）：目标 med 从 3261ms 压到 <1.5s（当前 <1.5s 仅 10%）；
- 专项二（会话退化）：重复场景按 20 分钟间隔排布，验证 30min ConnectionRefresh 后
  后段场景不再塌陷（对照 9/2 的 40%→23%→3.3%）；
- 4A70 云端零事件问题单独提给云端/轨迹导出侧核查。

## 4. 预期收益
- S1+S2 落地后丢帧 32%→~0、帧间隔 60→40ms：云端拿到完整实时音频，ASR 空识别 34.7% 应降至 <5%，
  WER 显著下降（9/2 词错 63% 是漏词，即缺音直接致错），VAD 命中率与延迟向 AEC-quiet 水平
  （469–557ms）靠拢，打断延迟 med 3.3s→<1.5s 可期。
- tai 重构的连接保活应先消除"后段场景塌陷"（③），这是重测最可能先看到的改善。
- S3+S4 落地后噪声场景打断命中率才可能起量（当前固定 600k 门下，9/2 那类 15–45 万的真实打断会被拒）。
