# 关于"误打断频繁、尾音难消除"的处理说明（含 AEC 参数设置）

> 针对贵司反馈的两个问题——TTS 播放期间误打断（barge-in 误触发）频繁、TTS 停止后尾音难以消除——以下说明我司的处理方案。核心结论：**光调 AEC 参数不够，误打断和尾音主要靠"AEC 参数 + 逻辑层门控"配合解决**，参数只是第一道防线。

---

## 一、AEC 参数：我们的设置 vs 贵司当前值

贵司当前使用的参数基本为 SDK 默认值。我们在默认值基础上做了一组**实测调优覆盖**（代码位置：`apps/common/config/user_cfg.c` 的 `get_cfg_file_aec_config()` 末尾）：

| 参数 | 贵司当前 | 我们设置 | 作用方向说明 |
|---|---|---|---|
| AEC_DT_AggressiveFactor | 1.0 | **2.0** | 回声路径追踪强度（范围 1~5），越大越快跟上喇叭回声变化 |
| AEC_RefEngThr | -70.0 | -70.0 | 参考信号能量门（-90~-60dB），维持默认 |
| ES_AggressFactor | -3.0 | **-6.0** | 非线性残留回声压制（范围约 -1~-5），越小（越负）压得越深 |
| ES_MinSuppress | 4.0 | **2.0** | 回声后级静态压制，与 ES_AggressFactor 配套实测调整 |
| ES_Unconverge_OverDrive | 4.0 | **2.0** | 我们直接设置为 = ES_MinSuppress（未收敛期同档压制） |
| DNS_gain_floor | 0.15 | **0.10** | 降噪增益地板（0~1），越小降噪越强 |
| DNS_over_drive | 1.0 | **2.0** | 降噪强度（0~6），越大越强，用于压掉 AEC 残留 |
| ANS_AggressFactor | 1.25 | 1.25 | 默认，未改 |
| ANS_MinSuppress | 0.04 | 0.04 | 默认，未改 |

**调参动机**：连续密集的 TTS 播放（如念故事、念数字串）时，AEC 残留回声仍会触发 VAD，造成 TTS 被自己的声音打断。加大 DT 追踪强度、加深 ES 压制、再叠加 DNS 二次压制后，回声残留被压到 VAD 触发阈值以下。

**验证方法**：TTS 播放期间读取 post-AEC 的 mic 数据并打印每帧能量占比（act%）。act 高（>50%）说明回声没消掉；act 低（<20%）说明 AEC 已生效。我们代码中的 `[AEC-DBG]` 诊断日志即做此用途，建议贵司保留同类日志作为调参依据。

> 注意：这组参数是针对我们的硬件（单 mic、近场使用）实测出来的组合，不是单参数理论推导。贵司 mic 增益、喇叭功率、结构腔体不同，直接照抄后仍需按上述验证方法微调。

## 二、误打断防护：三层防线

**第 1 层——AEC 压回声（参数层）**：见上表。目标是让回声残留在进入 VAD 之前就被压掉。这一层不行，后级逻辑再严密也会频繁误触。

**第 2 层——能量门 3/3 帧确认（关键）**：VAD 触发后**不立即**判定为用户说话，而是连续读取 3 帧（约 120ms）PCM 数据，**3 帧全部**满足每帧能量 Σ|int16| ≥ 100000 才确认为真人话音，否则视为回声残留/噪音丢弃。

- 实测发现：TTS 播报密集数字时，某个响音爆破会在 1~2 帧内冲过能量阈值。采用"2 帧中 2 帧达标"（2-of-2）规则会被这种瞬时 spike 骗过导致误切断播报，必须 **3-of-3** 才能滤掉 ≤2 帧的 spike。
- 真人说话 onset 通常持续 >120ms，可正常通过确认；代价仅是打断判定延迟约 40ms。
- 确认通过后，这 3 帧会作为 onset 补发进上行音频流（否则确认过程消耗掉的最响一段语音丢失，云端 ASR 只收到尾音/静音，导致打断后无播报）。

**第 3 层——1 秒冷却窗口**：一次打断触发后 1s 内忽略一切 TTS 到来/打断信号。老轮次被打断后在途 TTS 的残响不会引起二次连环触发（竞态窗口）。

## 三、尾音消除：两处排空

尾音问题的根源有两个，需分别处理：

**1. "云端发完 ≠ 喇叭播完"——等播放缓冲真正排空再恢复听音**

云端下发结束事件时，设备下行 jitter buffer 里可能还压着数秒 TTS 音频，喇叭仍在播放。若此时立即恢复听音，麦克风会采到还在播的尾巴，误判为新问题（自说自话）。

我们的处理：

- 收到本轮结束事件后，先等下行播放缓冲出现数据（确认本轮 TTS 确实到达，3s 超时兜底），再等缓冲**排空**（喇叭物理播完，35s 兜底）才恢复听音；
- 打断检测在这两段等待期间保持开启（用户改口不必等播完）。

**2. 喇叭刚停后的回声尾巴——排空 mic 缓冲约 300ms**

播放结束恢复听音前，连续排空 mic 采集缓冲 8 帧（约 300ms），清掉喇叭刚停后的回声尾巴/混响，再进入正常听音。

另外，打断（barge-in）后起新一轮上行前，也会先排掉 TTS 期间积压的旧 mic 数据（只保留最近 3 帧 ≈120ms 刚触发的话音），避免新上行先发送积压的静音/回声残响导致云端 ASR 收到垃圾或空文本。

---

## 四、建议的排查/调整顺序

1. **先照抄我们的 AEC 参数组**（上表"我们设置"列），用 post-AEC act% 日志确认 TTS 播放期间回声残留已压低；
2. 若仍有误打断：**提高能量门阈值**（我们的 100000 是单 mic 近场值，贵司应统计日志中真人说话的每帧 sum 值和噪音/回声的 sum 值，取分界线设门），确认规则务必用 3-of-3；
3. 尾音问题：确认是否实现了"等播放缓冲排空再听 + 恢复听音前排空 mic 300ms"。**如果没有这两处逻辑，光调 AEC 参数治不了尾音**——那不是回声残留问题，而是缓冲时序问题。

以上逻辑的完整实现可参考交付代码：`apps/common/config/user_cfg.c`（参数覆盖）与 `apps/common/LLM/tuya_agentic/tuya_agentic_demo.c`（能量门 `BARGE_MIN_ENERGY`、3/3 确认 `barge_in_energy_confirmed()`、冷却 `TUYA_BARGE_COOLDOWN_MS`、播放排空与 mic 排空逻辑）。

## 五、跟进：套用参数后误打断更频繁的回退与再调建议

如套用我们的参数组后误打断**变得更频繁**，说明这组"更强抑制"参数在贵司的声学环境（喇叭/腔体/mic 增益不同）产生了副作用。三个最可能的原因：

1. **ES_MinSuppress / ES_Unconverge_OverDrive 从 4.0 改 2.0 是把压制"调弱"了**——这两个值越大压制越强（见 SDK 注释）。4→2 削弱了 TTS 起播瞬间（自适应滤波器未收敛期）的静态压制，而那正是回声残留最大、最容易误触发 VAD 的时刻；
2. **DNS_over_drive = 2.0 过猛产生"音乐噪声"伪影**——过度降噪的典型副作用是离散频谱毛刺，瞬时能量反而会戳破 VAD 阈值，表现就是"越压越容易触发"；
3. **AEC_DT_AggressiveFactor = 2.0 在更非线性的回声通路上可能发散**——追踪越激进，遇到贵司喇叭/功放的非线性失真时自适应滤波器反而跟不上，残差变大。

### 第一步：回退到基线参数

| 参数 | 建议回退值 | 后续单参数调整方向 |
|---|---|---|
| AEC_DT_AggressiveFactor | **1.0** | 若连续 TTS 播放中仍误触发，逐步升 1.2 / 1.5；一旦更差立即回退 |
| AEC_RefEngThr | -70.0 | 保持 |
| ES_AggressFactor | **-3.0** | 确认回声残留仍高后再加深：-3.5 → -4.0 逐档试，不建议低于 -5 |
| ES_MinSuppress | **4.0** | 越大越强，误触发可试 5~6（上限 10） |
| ES_Unconverge_OverDrive | **4.0** | 与 ES_MinSuppress 同步调，TTS 起播误触发时优先加它 |
| DNS_gain_floor | **0.15** | 底噪压不住再降 0.1 |
| DNS_over_drive | **1.0** | 残留噪声仍响再升 1.3~1.5，不超过 2 |
| ANS_AggressFactor | 1.25 | 保持 |
| ANS_MinSuppress | 0.04 | 保持 |

即先恢复贵司原默认值，把参数变量清零，再按下面方法逐项验证。

### 第二步：按误触发发生的"时刻"定位，对症调参

用日志记录每次误触发的时间点，对号入座：

| 误触发时机 | 根因 | 处理 |
|---|---|---|
| TTS 刚起播的瞬间 | 滤波器未收敛期残差（Unconverge 压制不足） | ES_Unconverge_OverDrive / ES_MinSuppress 调大（5~6） |
| TTS 连续播放中途 | AEC/NLP 残留 | ES_AggressFactor 加深一档（-3.5/-4.0），或 DT 因子微升 |
| TTS 停止/句间停顿后 | 尾音/缓冲时序，**不是参数问题** | 必须实现"播放缓冲排空后再听 + mic 排空 300ms"逻辑（见第三节） |
| 随机分布、与 TTS 无关 | 降噪伪影（音乐噪声）或 AGC 放大残留 | DNS_over_drive 降回 1.0；临时关掉 aec_mode 里的 AGC 位对比测试 |

### 第三步：确认逻辑层是否已实现（比参数更重要）

参数只是第一道防线。**如果只套用了参数、没有实现第二节的能量门逻辑，误打断必然压不住**——请确认：

1. VAD 触发后是否有 **3/3 帧能量门确认**（3 帧全部达标才算真人说话，2-of-2 会被 TTS 爆破音 spike 骗过）；
2. 能量门阈值是否按贵司硬件标定：打印日志统计"TTS 播放期间 post-AEC 每帧 sum 值"与"真人说话每帧 sum 值"，取两者之间设门（我们的 100000 对应我们的 mic 增益，贵司直接照抄大概率不适用）；
3. 打断后是否有 1 秒冷却窗口。

调参方法上务必**一次只改一个参数**，每改一次做至少 10 分钟连续 TTS 播放测试，用"VAD 触发次数 + post-AEC act%"两个指标对比，有日志依据再固定。

## 六、外接功放喇叭场景的专项建议

贵司为外接功放喇叭方案，这一点对 AEC 调参影响很大，前面第五节的回退值需按本节修正：

**外接功放为什么特殊**：软件参考 AEC 的参考信号取自 DAC 数字输出（功放**之前**），而麦克风实际采到的回声经过了功放——

1. **回声被功放增益放大**：参考信号里不含功放增益，回声相对参考强得多，消除后残留天然更大；
2. **功放的非线性处理（EQ/DRC/限幅）无法被线性自适应滤波器建模**：AEC 线性消除部分大打折扣，残留回声主要靠 NLP/ES 的**静态压制**兜底——所以外接功放方案应走"高静态压制"路线，而不是深动态压制；
3. **功放 DSP 引入额外延时**：若回声延时超出 AEC 滤波器覆盖范围，AEC 基本失效，此时调任何压制参数都是隔靴搔痒。

### 外接功放推荐起步参数（替代第五节回退表）

| 参数 | 推荐值 | 说明 |
|---|---|---|
| AEC_DT_AggressiveFactor | **1.0** | 非线性通路禁激进追踪，防滤波器发散 |
| AEC_RefEngThr | -70.0 | 保持 |
| ES_AggressFactor | **-4.0** | 比默认深一档，压非线性残差 |
| ES_MinSuppress | **6.0** | 高静态压制，外放功放的主力防线（上限 10，残留仍高可到 8） |
| ES_Unconverge_OverDrive | **6.0** | 与上项同步，TTS 起播瞬间全靠它 |
| DNS_gain_floor | **0.10** | 辅助压残留 |
| DNS_over_drive | **1.5** | 辅助压残留，不建议超过 2（音乐噪声伪影反而触发 VAD） |
| ANS_AggressFactor | 1.25 | 默认 |
| ANS_MinSuppress | 0.04 | 默认 |

### 外接功放方案必查清单

1. **功放不能推到削波**：DAC 输出电平保持适中、增益交给功放做；DAC 电平过高 + 功放满增益 = 严重非线性失真，AEC 无解；
2. **核实回声延时**：若功放带 DSP 处理（有明显可感知延时），需实测并调整 SDK 的 `hw_delay_offset`（我们代码 `apps/common/LLM/audio/audio_input.c` 中 16k 采样率下当前为 50）；延时超窗时 AEC 消除率趋近于零；
3. **能量门 3/3 确认 + 按实测标定阈值**：外接功放下参数无法把残留压到万无一失，逻辑层是最终防线，必须实现（见第二节），阈值用贵司日志标定；
4. **AGC 核查**：残留被 AGC 放大回去了就是白压，误触发仍随机分布时可临时关闭 aec_mode 中的 AGC 位对比验证；
5. **硬件层终极方案（可选）**：从功放输出/喇叭线经分压电阻采样到 LINEIN 通道做硬件回采（`output_way = 1`），可把功放自身非线性纳入参考信号，是外接功放产品的经典解法——需要硬件增加采样电路，若贵司板子支持建议评估。

### 优先级总结（外接功放）

**排空逻辑 > 能量门 > ES 静态压制（MinSuppress/Unconverge）> DNS 辅助 > DT 追踪/ES 动态**。参数从上表起步后，仍按第五节"按误触发时刻定位"的方法逐项微调。

## 七、关于停说事件：ServerVAD 与 ChatBreak 的最终确认（TAI 2.1 协议）

**经与涂鸦云端团队确认：TAI 2.1 协议已移除 ServerVAD 事件，走 agenticKit（2.1 协议）的会话不会下发 ServerVAD。**

因此：

1. **开启 `asr.enableVad=true` 后，云端 VAD 判停说的通知信号就是 ChatBreak**。贵司日志"23 个 ChatBreak、0 个 ServerVAD"完全符合 2.1 协议现状，属正常行为而非异常；
2. DEMO 对 chat_break 按上下文区分语义：**上行（说话）期间收到 = 云端判停说**，结束上行、发 audio_end 进入处理；**TTS 播放期间收到 = 打断/停止播放**。每轮对话由 chat_break 结束上行，正是云端 VAD 正常工作的表现；
3. 开发文档中"ServerVAD 表示停说"的描述对应**旧版本协议语义**，未随 2.1 同步更新，设备侧应以云端实际下发行为为准（已向涂鸦云端核实）；
4. DEMO 中保留的 `TAI_EVT_SERVER_VAD` 处理分支源于协议枚举定义（事件号 5 在头文件中仍存在），属防御性兼容写法，在 2.1 会话中不会触发，无需改动；
5. 无论云端事件是否到达，DEMO 另有**本地静音约 2 秒超时兜底**，保证轮次不会因事件丢失而卡死。
